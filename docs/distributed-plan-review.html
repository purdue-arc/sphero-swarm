The one thing that blocks everything

Every network endpoint in this codebase binds to 'localhost' only. None of it is reachable from another machine today, and Electron's process model only knows how to launch local child processes. This has to change before any part of the distributed plan works — independent of every other design decision below.

The admin dashboard question

One already exists — the Electron + React GUI. It already gives you per-ball connection status and manual connect/disconnect/rehome (Controls tab), live algorithm/simulation state (Simulation tab), a camera stream (Perception tab), and constants editing (Config tab).

What it can't do yet: know about multiple Pis, keep a robot↔Pi registry, or start/stop a remote process — all downstream of the spawn()-is-local constraint above. The unified-gateway design sketched in architecture.html (built for a different problem — five uncoordinated local endpoints) turns out to be the right shape here too: one gateway on the mini-PC aggregating N Pi-side services behind a single websocket the existing GUI already knows how to consume.

Target architecture — where things end up

This is the end state after the "fix localhost / decide the protocol / per-Pi config" steps below are done. Two concrete calls are made here that the verdict table above left open:

  • The API lives on each Pi, and it's HTTP/JSON — not the old pickle-over-TCP socket. Pickle deserializing data that now crosses a real machine boundary is a code-execution risk; JSON isn't. Each Pi's Controls Service exposes the §8-style endpoints (/robots/:id/drive, /stop, /led, /health) bound to its real LAN address.
  • The algorithm/simulation "brain" (today's unmanaged gui_driver.py) moves into the mini-PC's Coordinator process — a supervised service, not a script someone remembers to launch in a terminal. It's the natural place for it: the Coordinator already holds the robot registry and is where perception feedback needs to land anyway.

Everything downstream of "Controls Service" on each Pi — the threading model, spherov2/Bleak connection handling, duration-bounded auto-stop, the disconnect watchdog — is the part of Controls_Server.py that already works and doesn't move. What changes is what wraps it: an HTTP layer facing the network instead of a loopback-only websocket + pickle socket, and a per-Pi robot subset instead of one global list.

Recommended order

  1. Fix the 'localhost' bindings — mandatory first step. Touches Controls_Server.py, gui_server.py, perception/server.py, gui_driver.py, and every GUI websocket URL.
  2. Decide the HTTP-API-vs-existing-protocol question (§8) explicitly — don't let it default silently either way.
  3. Build the per-Pi ball-roster config (their robots.yaml idea) — needed either way.
  4. Add reconnect-with-backoff (§9.4) and the systemd unit (§20) — needed either way.
  5. Decide what "emergency stop" actually does (§9.3) before building it — disconnect_all already does the heavy version.
  6. Only then extend the existing GUI into a multi-Pi-aware gateway consumer.

Everything else in the plan — safety timeouts, safe start/shutdown, the BLE/threading core, the model choice — is either already correct or already decided. Don't re-derive it; build on it.
