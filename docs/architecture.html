What's actually bad about this

  • gui_driver.py / gui_server.py run outside Electron's lifecycle. No auto-start, no auto-restart, no signal in the GUI they're supposed to be running. Forget to launch them and the Simulation tab just says "Reconnecting…" forever.
  • Five uncoordinated network endpoints — raw pickle TCP on 1235, websockets on 6767 / 6768 / 6769 / 6770 — no shared registry, no auth, no version negotiation on any wire format.
  • pickle over a raw socket is a latent code-execution risk if port 1235 were ever reachable beyond localhost.
  • Every component opens its own websocket. Controls.tsx alone opens both :6768 and :6769 itself; App.tsx opens :6769 again, separately.
  • No protocol versioning. A new Instruction.type or message shape breaks silently until both ends redeploy in lockstep.
  • Two disconnected sources of truth for what's running: Electron's IPC process table, and whatever's still open in a developer's terminal.

Why this is better

  • One supervised process table. The algorithm driver becomes a real Electron-managed service — status visible in the GUI, restarts on crash, no "did I remember to start this" failure mode.
  • One connection per renderer, one gateway process. Components subscribe to message types through shared context instead of each opening its own socket.
  • Structured, versioned messages replace raw pickle. Kills the deserialize-arbitrary-code risk; a new command type stops breaking whichever end hasn't redeployed yet.
  • Same domain boundaries, less accidental coupling. Controls still owns BLE, perception still owns the camera — the gateway routes, it doesn't absorb either service's logic.

A direction, not a mandate — a real refactor (new gateway process, message schema, Electron process-supervision changes) worth its own RFC via the controls-rfc skill before touching anything, not a same-day change.
